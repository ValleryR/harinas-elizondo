# Requirements

Summary of the team document (delivery 1) and the professor's functional requirements. Ids are stable, so use them in code comments, test names and the technical spec. Spanish terms are kept where they are the domain word (see [domain.md](domain.md)).

## Functional requirements (RF)

### RF-01 Access control
- Two user types. **Transaction users** (lab and Quality Control management) can do everything, which means registering clients, equipment, lots and analyses, issuing certificates and producing statistics. **Query users** (Quality Assurance, plant managers, the Operations Director) can only see reports, statistics and history.
- Permission levels differ between management and direction, limited by profile. The Manager and the Operations Director can see any report they need.
- Every action (create, update, issue) is recorded with the **employee id and the name** of who did it.

### RF-02 Lab equipment
- Create, read, update, deactivate and retire ("baja") equipment, for example alveographs and farinographs.
- The **equipment key is generated by the app**, random and unique.
- General data from the professor's list includes key, brand, model, serial number, long and short description, supplier, acquisition date, warranty and its expiry, location, responsible person and maintenance.
- When configuring equipment, the app asks for the parameters it analyzes and stores the **five main factors** with their international upper and lower limits. The mandatory parameters are listed in [domain.md](domain.md).
- If equipment has no reference values for every mandatory parameter, **it cannot be used for certification**.
- Equipment keeps a **change history**.
- Queries must show active, inactive and retired equipment.

### RF-03 Clients
- Create, read, update and deactivate clients that need a quality certificate. **Clients are never deleted**, only deactivated, and the reason is recorded.
- Clients are identified by the **same key used in SAP ByD**. In version 1 they are captured manually; version 2 would sync from SAP.
- Store general data (name, RFC, delivery address, the contact the certificate is addressed to) and, when they exist, the client's own reference values.
- International reference values live apart from client values. A client without its own values automatically uses the international ones.
- Input validation to avoid capture errors.

### RF-04 Inspections
- Manual capture of results per production lot.
- The **inspection sequence is generated and controlled by the system**, never typed. Letters A to Z, and after 26 inspections the sequence continues (we use AA, AB and so on).
- The certificate uses the **latest inspection** of the lot.
- A valid inspection belongs to the right lot and has all the data required for a certificate. Values out of range do **not** make it invalid; they show up later in the deviation column.
- Without a complete inspection the certificate cannot be generated.
- A new inspection can be created only after an **equipment failure and with authorization**.

### RF-05 Certificates
- Generated for clients who ask for one. Includes lot, purchase order, invoice, dates, analysis results, comparison with reference values and the resulting deviation. The professor's list adds requested quantity, total delivered quantity, shipping date and expiry date.
- Only issued when inspection data is complete, and results from **both machines** are mandatory.
- A **unique id** per certificate.
- Extra data (invoice, shipping data) must be filled before closing the certificate.
- Shows the responsible person's name and may require a digital signature, as the user decides.
- Out-of-range parameters appear in the deviation column.
- On generation the PDF is sent by default to the client contact and the Warehouse Manager.

### RF-06 Certificate delivery
- Email to the client and to the warehouse, automatic by default, with optional confirmation before sending.
- Store evidence of each delivery with date, responsible user and recipients.

### RF-07 History, reports and charts
- Keep an archive of every certificate issued.
- Statistics through reports and charts, by configurable periods, with filters.
- Only authorized users. Different access levels to reports.
- Export the certificate history to Excel so it can be used in Power BI.

### RF-08 Audit and change control
- Audit log for clients, equipment, inspections and certificates, with the user who acted.
- Inspection results **cannot be modified once used in a certificate**.

## Use cases (UC)

| Id | Name | Actor | Module route |
| --- | --- | --- | --- |
| UC-01 | Manage lab equipment and the parameters they analyze | Transaction user | `/equipos` |
| UC-02 | Manage clients, whether they need a certificate and their reference values | Transaction user | `/clientes` |
| UC-03 | Register inspections, with automatic sequence and latest inspection lookup | Transaction user | `/lotes`, `/inspecciones` |
| UC-04 | Quality analysis, comparing results with international or client values and flagging deviations without blocking | Transaction user | `/inspecciones` |
| UC-05 | Generate certificate from the lot's latest inspection plus client data, references, invoice and dates | Transaction user | `/certificados` |
| UC-06 | Send certificate by email to client and warehouse, storing evidence | System | `/certificados` |
| UC-07 | Print certificate for the delivery paperwork | Warehouse clerk (receives it by email) | PDF |
| UC-08 | View history, reports and statistics | Query user | `/reportes` |

Actors in the team document are Transaction user, Query user, Warehouse clerk ("Almacenista"), Client (external) and System. The professor's case study lists finer-grained scenarios (2.2.1 to 2.2.10, for example "Alta de Equipo", "Registro de análisis inicial / subsecuentes", "Impresión de certificados") that map onto these use cases.

## Quality characteristics (non-functional)

From the team's technical sheet. Each one needs evidence in the final delivery.

| Characteristic | Indicator | Evaluation criterion | Evidence we plan |
| --- | --- | --- | --- |
| Security | Access restricted by profile | Only authorized users reach functions for their role | Role checks in the data access layer plus tests per role |
| Reliability | Data validated before issuing | No certificate with incomplete information | Unit tests of BR-CER-* and an integration test of the issue flow |
| Information integrity | Audit log and change control | Data cannot change without a record | Audit rows on every mutation, locked inspections |
| Availability | Access during working hours | System available during normal operation | Vercel deployment, uptime note |
| Usability | Clear interface, simple navigation | Users finish tasks without frequent errors | UAT script with task success and error counts |
| Maintainability | Modular architecture (explicitly "not a monolith") | Changes do not affect other functions | Layered folders, domain logic isolated and unit tested |
| Traceability | Actions logged per user | Every operation in the audit log | `/bitacora` screen and export |
