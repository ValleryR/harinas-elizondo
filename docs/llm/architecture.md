# Architecture

## 4+1 views mapped to the code

The team document describes a layered system (presentation, business logic, data access, services and integration) running as a centralized web app. This is how each layer lands in a Next.js app.

| Layer (team doc) | Where in the repo |
| --- | --- |
| Presentation (login, menu, module screens) | `src/app/**/page.tsx`, `src/components/` |
| Business logic (rules, validations, latest inspection, deviation, sending, audit) | `src/lib/domain/` (pure, unit tested) and server actions per module |
| Data access (repositories per entity) | `src/lib/db/` (Drizzle schema and client), one data access file per module when it is built |
| Services and integration (email, Excel export, Power BI) | `src/lib/services/` (to create) |
| Physical view (app server, DB, mail service, analysis tools) | Vercel (app), Neon Postgres (DB), Resend (email), Excel/CSV export |

```
├── components/
│   ├── ui/               ← shadcn components (base-ui flavor). Do not edit by hand unless needed
│   └── *.tsx             ← app components
└── lib/
    ├── domain/           ← pure business rules + *.test.ts next to them
    ├── db/               ← schema.ts, auth-schema.ts, index.ts (lazy getDb)
    ├── auth.ts           ← lazy getAuth(), roles
    ├── auth-client.ts    ← browser auth client
    ├── modules.ts        ← nav + module metadata (single source)
    └── utils.ts          ← cn()
legacy/prototipo-v0.1/    ← old prototype, reference only, excluded from lint
drizzle/                  ← generated migrations (after the first db:generate)
```

Suggested shape for a module when it is built, for example clients:

```
src/app/(app)/clientes/
├── page.tsx              ← list (server component, reads via data layer)
├── nuevo/page.tsx        ← create form
├── [id]/page.tsx         ← detail and edit
├── actions.ts            ← "use server" mutations. Validate with zod, check role, write audit row
└── data.ts               ← "server-only" queries for this module
```

## Next.js 16 rules (read before coding)

This is Next.js 16.4 with **Cache Components enabled** (`cacheComponents: true`). Training data about older Next.js is often wrong here. The bundled docs in `node_modules/next/dist/docs/` are authoritative.

- Reading `cookies()`, `headers()` or the session outside a `<Suspense>` boundary is a **build error**. Keep the shell static and read the session inside a component wrapped in `<Suspense>`. Guide at `node_modules/next/dist/docs/01-app/02-guides/authentication-with-cache-components.md`.
- Do not await the session at the top of a layout.
- Middleware is now `proxy.ts` (`01-app/01-getting-started/16-proxy.md`). Use it only for optimistic redirects. Real authorization happens in the data layer and server actions.
- `LayoutProps<"/route">` and `PageProps<"/route">` are global types generated by `next typegen` (the `typecheck` script runs it).
- `getDb()` and `getAuth()` are lazy so `next build` works without env vars. Never create the DB client at module top level.

## Language rules

- Code is English. That covers identifiers, file names, DB tables and columns, commit messages and code comments.
- Everything the end user sees is Spanish. That covers UI text, routes (`/clientes`), validation and error messages, toasts, emails and the PDF.
- Agent docs (this folder, `AGENTS.md`) are English. Human docs exist in English (`README.md`) and Spanish (`README-es.md`).

## UI stack and design

| Need | Use | Why |
| --- | --- | --- |
| Components | shadcn on **base-ui** (`components.json` style `base-nova`), Tailwind v4 | Accessible primitives, owned code |
| Class names | `cn` from `@/lib/utils` (shadcn's `cn` package), `cva` for variants | Already wired by shadcn |
| Toasts | Sonner (`<Toaster />` in the root layout) | |
| Charts (RF-07) | recharts, install when building reports | Curated pick |
| Animation | CSS transitions first, `motion` only for springs or layout animations | |
| Command menu (optional) | cmdk | |
| Long tables | Virtuoso if a list passes ~1,000 rows | |
| Forms | zod for validation, server actions for mutations | |

Design skills to load before UI work (install with `npx skills add emilkowalski/skills` if missing):
- `emil-design-eng` for polish, motion decisions, press feedback, easing.
- `apple-design` for restraint, typography, materials and spacing.
- `pick-ui-library` before adding any new UI dependency.

House style so far is quiet and dense, like an internal tool. Neutral palette, Geist, small type, 150 ms color transitions, `active:scale-[0.97]` on pressable things, no animation on keyboard actions, and `prefers-reduced-motion` respected.

## Data and auth

- Postgres on Neon (via Vercel Marketplace), Drizzle ORM with `casing: "snake_case"`, migrations in `drizzle/`.
- Better Auth with email and password. Extra user fields `role` and `employeeId`. Users come from a seed script and a Usuarios screen, public sign-up is off (D-14).
- Certificates are rendered with `@react-pdf/renderer` and emailed with Resend (D-13).
- Authorization rule of thumb. Pages decide what to show, server actions and data functions decide what is allowed. Always check the role server-side.
